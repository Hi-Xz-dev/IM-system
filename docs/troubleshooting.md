## 01 多端房间成员状态不一致

**当前状态：代码已修复，边界已确定，定向服务层测试及竞态检查通过；仅待真实客户端联调验收。此前“加入与新连接继承规则仍待确认”的描述已过时。**

**位置：** [room_manager.go](../server/room_manager.go) 的 `leaveRoomUnsafe`、`LeaveRoomH`、`JoinRoomH`、`JoinRoom`；[user_service.go](../server/user_service.go) 的 `Online`、`Offline`。

**原问题：** `leaveRoomUnsafe` 删除房间里该用户的所有 session，但只清理传入 session 的 `JoinedRooms`；`LeaveRoomH` 找到已加入的连接后却传入 `users[0]`。

**本次进展：** 主动退房已同步清理同账号所有已加入连接，`LeaveRoomH` 使用实际匹配的连接；新增 `removeRoomSessionUnsafe` 供 `Offline` 使用，断线只移除当前 session，最后一个 session 离开后才移除账号成员项；第 06 项进一步调整为空房保留。回归用例见 [room_session_test.go](../server/room_session_test.go)，覆盖命令与 HTTP 业务入口主动退房、单端断线后另一端继续收消息、重复断线、最后连接清理和断线后主动退房；这些是服务层测试，未覆盖真实网络握手。

**加入同步进展：** HTTP 和命令加入、创建运行时房间共用账号级加入函数；单连接加入幂等，避免多次继承导致重复投递。`Online` 在同一把写锁内继承其他在线端房间，因此加入与新端登录无论谁先发生，最终成员状态都一致。所有端离线后不会从数据库恢复成员关系。房间资料的启动加载与空房保留见第 06 项。

**检查步骤：** A1、A2 都加入同一房间，B1 留在该房间。分别测试 A1 正常退出、直接断开、HTTP 退出；随后让 A2 执行 `where`、发送房间消息，并接收 B1 的消息。再测试 A1 先加入、A2 后登录，以及 A1 未加入但 A2 已加入时调用 HTTP 退出。

**修复方向：** 明确账号成员关系与连接订阅关系；断开单个连接时只清理对应订阅，显式退出则按约定同步账号状态。

- [x] 加入、退房、断线与新端继承的服务层用例检查房间索引和相关连接的成员状态。

## 02 TCP 认证与业务命令连续发送时可能丢失

**状态与范围：暂缓处理，未修复。** 本项仅涉及 8080 原始 TCP 入口。当前网页先通过 HTTP 登录获取 Token，再建立 WebSocket 并自动发送认证消息，使用 WebSocket 消息读取，不存在本项的 Scanner 更换问题。TCP 客户端若严格等待认证成功响应后再发送命令，通常不会触发预读后续命令的场景；连续发送认证与业务命令仍有风险，不能将本项标记为不存在。

**位置：** [handler.go](../server/handler.go) 的 `Handler`、[tcp_reader.go](../internal/connection/tcp_reader.go) 的 `NewTCPReader`。

**现状：** 认证使用一个 Scanner，认证成功后重新创建 Scanner；旧 Scanner 可能已经预读后续命令。另外，启动发送 goroutine 后，认证成功提示仍直接写连接，发送出口没有完全统一。

**检查步骤：** TCP 客户端在一次写入中发送 `auth|有效token\nwho\n`，保持连接打开，检查是否收到 `who` 的响应；再测试拆成多次写入和多条命令连续写入。

**修复方向：** 认证和业务阶段复用同一个缓冲读取器；上线后输出统一进入发送通道。

- [ ] 连续发送与分段发送均不丢命令，顺序符合协议。
- [ ] 已认证连接的业务输出只有一个写入所有者。

## 03 私聊投递失败仍返回成功

**当前状态：代码已修复。** 保留底层成功入队计数；`PrivateChat` 收到错误后反馈失败并立即返回，成功提示改为“私聊消息已进入发送队列”，离线提示改为“用户当前不在线”。读取在线 session 列表时在锁内复制切片，避免锁外遍历共享数组。定向回归用例见 [private_delivery_test.go](../server/private_delivery_test.go)。

**位置：** [message.go](../server/message.go) 的 `SendPrivateMessage`；[user_service.go](../server/user_service.go) 的 `PrivateChat`；[user.go](../user/user.go) 的 `SendMsg`。

**原问题：** 有两层错误处理缺口：目标发送队列满时返回错误，但 `SendPrivateMessage` 只记录日志，最终仍返回 `nil`；即使该函数因编码或资料缺失返回错误，`PrivateChat` 也只记录日志、没有提前返回，仍会发送“私聊发送成功”。目标离线则被描述为“用户不存在”，混淆了账号存在性与在线状态。本项属于 TCP 和网页 WebSocket 共用的私聊业务。

**检查步骤：** 使用不消费消息的测试连接填满接收队列，再发私聊；分别模拟所有目标失败、部分目标成功和目标离线。

**修复方向：** 区分服务端接收、入队、落库、写连接和客户端确认；返回与当前承诺匹配的结果。部分 session 失败时采用什么策略也要写清楚。

**本次实现范围：** 不增加客户端 ACK；至少一个目标在线连接成功入队，才按“已进入发送队列”反馈成功；全部入队失败则返回错误，上层反馈失败并立即返回。部分端失败保留日志，不承诺所有端均已收到。持久化仍在投递前异步入队，投递失败不代表消息没有保存；持久化可靠性留在第 08 项。

**慢连接策略（2026-11-02）：** 每个连接保留容量 100 的 Channel。队列满立即返回 `ErrSendQueueFull`，首次失败开始 5 秒拥塞计时，不立即断开；成功完成一次网络写入且队列有空位时取消计时。宽限期内未观察到恢复则关闭当前连接；已关闭连接拒绝后续入队。TCP 和 WebSocket 每次网络写入均设置 5 秒截止时间，写失败会关闭连接并通知清理。计时器只在出现队列满时创建，一个拥塞阶段只保留一个，不自动重试失败消息，也不保证断线补拉。5 秒是初始策略值，需要慢客户端联调后调整；其他正常连接继续投递。

- [x] 全部目标入队失败时不再报告投递成功。
- [x] 部分成功、全部失败、离线三个场景有明确结果，并有服务层回归测试。
- [x] 未实现客户端 ACK 时，不把入队成功描述为“对方已收到”。
- [ ] 真实客户端联调验收。

## 04 连接退出后发送 goroutine 可能泄漏

**当前状态：代码已修复，定向竞态测试通过，待真实客户端联调验收。** 本项的退出信号、幂等关闭和写失败清理已随慢连接处理补齐，本次核查无需新增业务代码。

**位置：** [user.go](../user/user.go) 的 `ListenMessage`、`Close`；[user_service.go](../server/user_service.go) 的 `Offline`。

**原问题：** `ListenMessage` 阻塞读取 `User.C`，但 `Offline` 只关闭网络连接；队列为空时关闭连接不能唤醒 Channel 读取。写失败时断线通知队列满也会直接丢弃通知。

**本次进展：** `Close` 幂等地关闭独立退出信号并取消拥塞计时器，不关闭发送 Channel；`ListenMessage` 可在空闲时被唤醒退出，写失败也先关闭底层连接再尝试通知 Server。通知队列满时不阻塞退出，实际 TCP/WS 读循环通过连接关闭后的读取错误继续执行 `Offline`。发送与关闭使用独立锁协调。新增测试覆盖空闲退出、通知队列满以及并发发送和关闭；真实连接读循环与在线状态清理仍待联调，不将第 04 项整体标记为已验收。

**检查步骤：** 批量建立、认证并断开空闲连接，不再向它们发送消息；等待清理后查看 goroutine 数量和堆栈是否持续残留在 `ListenMessage`。

**修复方向：** 设计统一的取消信号和幂等关闭流程。不要直接在多个路径随意关闭 `User.C`，否则并发发送可能触发 `send on closed channel`。

- [ ] 空闲连接关闭后，读写 goroutine 均在约定时间内退出。
- [ ] 并发发送、重复关闭、断线事件拥塞都不 panic、不长期残留连接。

**已完成的定向验证（2026-11-02）：** `TestCloseStopsIdleWriterWithFullDisconnectQueue`、`TestConcurrentSendAndCloseStopsWriter`、`TestSustainedCongestionClosesOnlySlowConnection`、`TestListenMessage` 的竞态检查通过，覆盖空闲发送循环退出、断线通知队列满、并发发送与关闭、拥塞关闭及写失败。以上使用测试连接，不表示已完成真实 TCP/WS 的读循环、在线状态清理和长期 goroutine 数量验收；上面的端到端验收框继续保留。

## 05 并发字段与快照边界不完整

**位置：** [user.go](../user/user.go) 的 `UpdateActiveTime`；[cleaner.go](../server/cleaner.go)；[lifecycle.go](../server/lifecycle.go) 的 `Start`、`Shutdown`；[user_service.go](../server/user_service.go) 的 `PrivateChat`。

**原问题：** `ActiveTime` 写入不使用清理线程读取时的同一同步机制；`IsShutdown` 与监听器发布、读取未同步。`PrivateChat` 从在线表取得 session 切片后解锁，却没有复制底层数组，并发下线可能修改共享切片。

**修复范围（2026-11-02）：**

- 活跃时间改为私有 `atomic.Int64`，只通过 `UpdateActiveTime` 和 `LastActiveTime` 原子存取；清理扫描每次读取一次时间值。不能再直接赋值 `ActiveTime` 字段。
- 新增 `lifecycleMu`，统一保护 `listener` 和私有 `isShutdown`；`Shutdown` 在锁内设置关闭状态、取得监听器，在锁外关闭。`Start` 发布监听器前在同一把锁下检查关闭状态，若关闭已开始则立即关闭新监听器并返回。没有将网络 IO 放在锁内。
- 私聊已在第 03 项修复：锁内复制目标连接切片，锁外投递；复制隔离的是切片底层数组，连接本身仍可能关闭，交由 `SendMsg` 拒绝关闭后的入队。
- `User.IsClosed` 的运行时访问仍由 Server 的 `mapLock` 保护；它是在线成员清理标志，与发送生命周期的私有 `closed` 分别归不同锁管理。

本项不代表全项目所有并发问题均已解决。扫描后到执行清理前的活跃状态变化、关闭期间的所有连接接入与后台 worker 退出不在本次修复范围，完整退出流程继续看第 09 项。

**检查步骤：** 在 Race Detector 下并发更新活跃时间与清理，并发私聊与同账号连接上下线，以及并发启动与关闭。测试要实际触发这些访问，不能只看普通用例是否通过。

**修复方向：** 为每个共享字段确定锁或原子操作；需要锁外遍历时复制切片。不要把“拿到切片变量”当作完成独立快照。

- [x] 活跃时间并发读写与清理扫描、监听器发布与关闭、私聊与多端上下线的定向竞态测试通过。
- [x] 关闭状态、监听器发布和活跃时间访问的同步规则明确。

新增回归用例位于 [activity_test.go](../user/activity_test.go) 和 [concurrency_test.go](../server/concurrency_test.go)。监听器用例使用测试监听器验证发布与关闭的交错顺序，不代表已完成真实网络启动和完整退出验收。

## 06 房间持久化、恢复与创建失败补偿缺失

**当前状态：代码已修复，待真实 MySQL 与服务重启联调验收。**

**最终边界：** 房间资料持久化；无人在线也保留，所有端离线仅清除参与状态，再登录需重新加入。暂不设置房主、解散权限或永久成员关系。

**位置：** [room_manager.go](../server/room_manager.go) 的 `CreateRoomForUser`、`LoadRooms`、`leaveRoomUnsafe`、`removeRoomSessionUnsafe`；[handler.go](../internal/httpserver/handler.go) 的 `CreateRoom`；[main.go](../cmd/server/main.go)；[room_repository.go](../internal/repository/room_repository.go) 的 `FindAll`。

**原问题：** 退房、断线只删除内存空房，数据库记录保留，同名创建又被唯一约束拒绝；重启后未加载已有房间。HTTP 先写库再检查在线连接，可能记录已创建却返回失败。

**修复（2026-11-03）：**

1. 取消退房和断线时的空房删除，只清理成员；空房仍可查询、重新加入。
2. 新增仓储 `FindAll` 和 Server `LoadRooms`，在开放 TCP/HTTP 入口前加载房间 ID、名称，成员列表初始化为空。加载失败则停止启动，不以空列表继续服务。
3. HTTP 与命令创建统一走 `CreateRoomForUser`：写库成功后发布内存房间，并同步加入当前在线端。已登录用户无聊天连接或在写库期间断线时，创建空房仍返回成功，不再依赖在线状态来判定创建成功。
4. 移除旧的分离式 `CreateRoomRecord` / `CreateRoomRuntime` 流程。同名房间返回冲突，原房间仍可查询、加入，无需删库重建。
5. `RoomRepository` 抽象出创建和加载两个方法，便于注入测试仓储；未新增表或成员持久化功能。

创建成功与自动加入是两个结果：房间保存后，即使创建者断线也保留。进程若在写库后、内存发布前崩溃，下次正常启动通过加载恢复；不承诺数据库与内存具有跨进程原子事务。

- [x] 服务层覆盖创建、清空、重新加入、模拟重启加载及不恢复成员身份。
- [x] 服务层覆盖写库失败、加载失败、同名冲突、无连接创建和写库期间断线。
- [x] HTTP handler 测试覆盖无聊天连接创建成功、同名冲突与数据库错误；使用注入身份和测试仓储，不代表 JWT 或真实 MySQL 已验收。
- [ ] 使用真实 MySQL 启动服务，创建房间、全部退出、重启后确认原 ID/名称保留、人数为 0，并可再次加入。

回归用例：[room_persistence_test.go](../server/room_persistence_test.go)、[room_create_test.go](../internal/httpserver/room_create_test.go)。

## 07 Token 日志与密钥配置

**位置：** [auth.go](../server/auth.go) 的 `authenticateConnection`；[gateway.go](../gateway/ws/gateway.go) 的 `Auth`；[config.go](../internal/config/config.go)。

**现状：** 认证原文 `raw` 和解析后的 `args` 都会写日志，其中包含完整 JWT；JWT 默认密钥为硬编码的 `xx`。

**检查步骤：** 使用专门测试账号认证，检查认证日志字段；移除或设置无效密钥，检查服务启动行为。不要把真实 Token 复制到排查记录里。

**修复方向：** 删除敏感日志字段，用连接标识、认证结果等定位问题；密钥从外部配置读取，缺少有效配置时给出明确启动错误。

- [ ] TCP/WS 认证成功和失败日志均不包含完整凭据。
- [ ] 有清晰的本地配置方式，无生产可误用的固定弱密钥。

## 08 持久化失败和队列积压策略不足

**位置：** [message.go](../server/message.go)、[message_persist.go](../server/message_persist.go)、[mysql.go](../internal/database/mysql.go)。

**现状：** 一个 worker 逐条写库，失败只记录日志；`PersistQueue <- msg` 在满队列时阻塞发送链路；后台写库使用 `context.Background()`，没有应用层操作截止时间。

**检查步骤：** 在独立测试环境中模拟写库失败、延迟和超时，观察消息是否送达、是否落库、队列长度和发送延迟；恢复数据库后检查处理结果。

**修复方向：** 先定义接受与持久化成功的关系，再选择超时、有限重试、拒绝接收或补偿策略。若重试，需要考虑幂等；先不引入 MQ 也可以把行为设计完整。

- [ ] 队列满和写库超时不会造成没有上限的业务等待。
- [ ] 落库失败可观测，处理策略明确且可以验证。
- [ ] 能说明内存队列在进程崩溃时的数据损失边界。

## 09 关闭流程不完整，启动错误没有统一反馈

**位置：** [lifecycle.go](../server/lifecycle.go)、[cleaner.go](../server/cleaner.go)、[disconnect.go](../server/disconnect.go)、[broadcaster.go](../server/broadcaster.go)、[main.go](../cmd/server/main.go)。

**现状：** 关闭只停止 TCP 接入并关闭当前在线连接，没有等待持久化队列、发送任务和后台循环结束，也没有协调 HTTP 关闭。TCP 监听失败仅返回，HTTP 的 `r.Run` 错误未处理，进程可能只启动了一部分功能。

**检查步骤：** 持续发消息时发送 SIGTERM，比对已经承诺接收的消息与落库结果；分别预占 TCP 和 HTTP 端口后启动，检查日志、进程状态和健康接口。

**修复方向：** 统一管理启动错误、取消信号、停止接入、队列处理和 worker 等待，设置退出期限。不要在生产者仍运行时直接关闭其写入的队列。

- [ ] 启动失败能明确反馈，不静默进入部分可用状态。
- [ ] 正常退出按约定处理已接收消息，并在期限内结束。
- [ ] 后台任务可独立停止和验证，不依赖进程退出强制回收。

## 10 昵称持久化与 Profile 生命周期

**位置：** [user_service.go](../server/user_service.go) 的 `Rename`、`RenameH`、`Online`、`Offline`、`nameExistsUnsafe`。

**现状：** 改名只更新内存 Profile；数据库昵称未更新，登录仍从数据库读取。最后一个连接离线后 Profile 未删除，长期运行时会保留曾登录用户资料，重名检查也会扫描这些资料。

**检查步骤：** 改名后调用登录、建立新连接并重启服务，对比昵称；大量不同账号登录退出后检查 Profile 数量；检查重名规则是否与注册流程一致。

- [ ] 昵称的权威来源明确，登录、在线展示和重启结果一致。
- [ ] Profile 有明确的保留、清理或缓存淘汰策略。
- [ ] 昵称是否允许重复的规则在注册和改名中一致。

## 11 连接资源边界不足

**位置：** [handler.go](../server/handler.go)、[gateway.go](../gateway/ws/gateway.go)、[websocket.go](../internal/connection/websocket.go)、[tcp_reader.go](../internal/connection/tcp_reader.go)、[cleaner.go](../server/cleaner.go)。

**现状：** 认证前没有读取截止时间；WS 没有显式读消息大小限制和写截止时间；TCP 依赖 Scanner 默认大小限制，两种协议的超长消息行为未统一。活跃时间仅由应用消息更新，长期只接收消息的用户也会被当成空闲连接清理。

**更新：** WebSocket 写截止时间已补为每次 5 秒，与 TCP 一致；发送队列也增加持续拥塞关闭策略。其余认证超时、读取大小与心跳边界仍未修复。

**检查步骤：** 建连后不认证、只发半条命令、发送超长消息、客户端停止读取、正常客户端长期只收不发；另在本地检查注册登录和消息发送高频请求的资源占用。

**修复方向：** 定义认证超时、消息长度、写超时、心跳与空闲策略，并设置与本项目规模匹配的限流和连接上限。WS Origin 规则按实际部署来源配置，不能把 Origin 检查当作身份认证。

- [ ] 未认证、慢读和异常大小请求在明确期限内被处理。
- [ ] TCP/WS 对长度与异常连接有可说明的统一规则。
- [ ] 心跳、网络存活与用户发言活跃度的用途区分清楚。

## 12 房间历史权限需要业务确认

**位置：** [handler.go](../internal/httpserver/handler.go) 的 `RoomHistory`、`Members`；[room_manager.go](../server/room_manager.go) 的 `RoomHistory`、`Members`。

**现状：** HTTP 和命令入口的房间历史查询没有成员校验；TCP 成员列表要求入房，HTTP 成员列表没有同样限制。这是规则不明确，不能在没有业务定义时直接判定所有读取都是越权。

**检查步骤：** B 未加入 A 的房间，分别通过 HTTP 和 TCP/WS 查询历史与成员；再检查成员退出后、新加入成员是否应该看到过去消息。

- [ ] 写明公开房间、成员可见、退出后可见性等实际采用的规则。
- [ ] 所有入口按相同规则鉴权，有允许和拒绝场景测试。

## 13 消息标识、历史分页与协议语义

**位置：** [message.go](../internal/domain/message.go) 的 `NewMessage`；[message_service.go](../internal/message/message_service.go) 的 `toDomainMessages`；[message_repository.go](../internal/repository/message_repository.go)；[003_create_messages.sql](../migrations/003_create_messages.sql)。

**现状：** 实时消息 ID 未生成，历史转换未携带数据库 ID；历史固定取 20 条，没有继续翻页游标。查询只按 `created_at` 排序，表中 DATETIME 未指定小数秒精度，同时间消息没有唯一排序依据。认证等部分输出为纯文本，历史命令又把结构化消息格式化为系统文本。

**检查步骤：** 快速发送超过 20 条带编号消息，比对实时与历史 ID、排序和可继续读取性；用统一客户端解析认证、聊天、错误、历史响应。

**修复方向：** 先补有效 ID、稳定排序与游标设计；约定消息与错误的协议结构。客户端 ACK、去重和断线补拉作为后续能力，需要先定义交付语义再实现。

- [ ] 实时与历史消息可用稳定标识关联，排序不依赖不唯一的时间值。
- [ ] 若承诺完整历史，超过 20 条后可继续分页，连续翻页不重复、不遗漏。
- [ ] 客户端能明确区分聊天消息、系统通知、响应和错误。

## 14 多入口业务规则重复，接口返回对象边界不清

**位置：** [room_manager.go](../server/room_manager.go)、[user_service.go](../server/user_service.go)、[room_service.go](../internal/service/room_service.go)、[router.go](../internal/httpserver/router.go)、[handler.go](../internal/httpserver/handler.go)。

**现状：** HTTP 与命令入口分别承担成员更新、通知、校验和持久化等逻辑，已有行为差异；部分 `:user` 参数实际上被忽略，以 JWT 身份为准。`GetMembers` 返回 `*user.User`，HTTP 会序列化导出的运行时字段，而模型还包含 Channel 等不适合 JSON 的字段，需要验证实际响应是否失败。

**检查步骤：** 对创建、加入、退出、改名逐项比较 HTTP 与 TCP/WS 结果和通知；请求成员列表，检查 HTTP 状态、实际响应体及序列化错误，不能只检查状态码。

**修复方向：** 让不同协议调用同一份业务操作，入口负责解析和响应；使用成员 DTO，只暴露客户端需要的字段；整理当前用户接口的路径含义。

- [ ] 同一业务动作从不同入口执行，核心结果和错误规则一致。
- [ ] 成员接口稳定返回可解析 JSON，不直接暴露运行时连接对象。
- [ ] 文档、路径参数与实际身份来源一致。

## 15 测试与性能验证证据不足

**位置：** [server 测试目录](../server)、[认证测试](../internal/auth/service_test.go)、[消息服务测试](../internal/message/message_service_test.go)、[消息仓储测试](../internal/repository/message_repository_test.go)、[广播基准](../server/message_benchmark_test.go)、[房间基准](../server/room_manager_benchmark_test.go)。

**验证安排：**

1. 为 01–14 中已确认的问题补最小回归用例，异步结果通过事件、条件等待和截止时间判断。
2. 区分纯单元测试与数据库集成测试，提供独立数据库的初始化和清理方式。
3. 执行普通测试与竞态测试；命令未成功运行不算通过。
4. 用真实 TCP/WS 客户端压测，记录机器、连接数、消息大小、发送速率、房间分布和是否落库。
5. 同时统计实际接收数、失败/丢弃数、P95/P99 延迟、CPU、内存、goroutine 和队列积压，再决定是否需要优化锁、批量写库或分布式。


- [ ] 关键边界有回归测试，单元与集成测试可独立运行。
- [ ] 完成竞态检查，记录执行环境和结果。

## 暂不作为必修项的扩展

- P3：多节点网关、跨节点消息路由、Redis 在线状态、MQ、服务发现。
- P3：完整离线消息、客户端 ACK 与重试去重、跨端历史同步。这些能力若决定实现，应单独定义验收范围。
